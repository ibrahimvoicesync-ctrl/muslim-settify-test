## Planning notes

**Assumption-delta: explicit add-alongside decision.** This phase introduces a 4th member of what has been a fixed set of 3 hardcoded brands. The assumption-delta scan flags this singular-to-plural transition as worth naming rather than absorbing silently. The recorded decision is **add-alongside, not generalize**: a 4th hardcoded constant plus a 4th conditional block, matching the existing convention exactly (D-01, D-03, D-04). A generalized brand-list or config-driven routing table was considered and rejected for this phase because (a) it would rewrite the three existing conditional blocks, which D-04 explicitly forbids, (b) the codebase has no test infrastructure, so refactoring live routing for three production brands carries real regression risk with no safety net, and (c) at four brands the conditional chain is still the clearest expression of intent. Trade-off acknowledged: if a 5th or 6th brand arrives, revisit and promote to a table-driven map then. This note exists so the decision is on the record rather than an accident of momentum.

**API coverage checkpoint: not applicable.** The api-coverage detector returned `detected: false` for this phase's scope. The only integration here is a hardcoded outbound redirect URL pointing at a Typeform link — no SDK, no API client, no authentication, and no capability surface to enumerate. No `COVERAGE.md` is produced, and that is correct rather than an omission.

**Schema push gate: not applicable.** No Payload, Prisma, Drizzle, Supabase, or TypeORM schema files exist or are touched. No blocking schema push task is needed.

**Flagged assumption, carried not resolved here.** The placeholder Typeform URL is intentionally non-functional until Phase 3. Between the end of this phase and the completion of Phase 3, `h.muslimsettify.com/apply` will redirect to a Typeform link that does not resolve to a real form. This is the accepted trade-off recorded in D-02 (do not block Phase 1 on Typeform creation), but it means the new subdomain must not be advertised, linked from ads, or treated as capturing leads until Phase 3 swaps in the real form ID.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Internet client to Vercel Edge to Next.js Server Component | The `Host` request header crosses this boundary and is the sole untrusted input consumed by `resolveTypeformUrl` |
| Next.js Server Component to external Typeform origin | The outbound HTTP redirect target crosses this boundary and is returned to the client's browser |
| Repository source to build pipeline | `scripts/check-no-direct-typeform.mjs` is the gate that constrains where Typeform links may appear in source |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Spoofing | `Host` header consumed by `resolveTypeformUrl` in `app/apply/page.tsx` | low | accept | An attacker-supplied `Host` header can only select among four fixed hardcoded constants or fall through to the `TYPEFORM_URL` env fallback / misconfiguration page. It cannot introduce a new destination. Already documented as an accepted, mitigated risk in `.planning/codebase/CONCERNS.md`; this plan introduces no new exposure. |
| T-01-02 | Tampering | Redirect target construction in `resolveTypeformUrl` | high | mitigate | Open redirect is prevented by design and this plan preserves that design: the new branch performs a strict-equality comparison against a single fixed hostname from a closed allowlist, and returns a module-level string literal. The header value is never interpolated into, concatenated with, or used to construct the redirect URL, a file path, or a shell command. Enforced by the acceptance criterion asserting exactly two `H_MUSLIMSETTIFY_TYPEFORM_URL` occurrences (declaration plus return) and by the five-host behavioral probe in Task 2 — a dynamically-constructed target would surface as an unexpected `Location` on the `www.muslimsettify.com` canary. |
| T-01-03 | Information Disclosure | Placeholder Typeform URL shipped to production ahead of Phase 3 | medium | mitigate | The placeholder value is deliberately self-describing and non-resolving, so it cannot be mistaken for a working form by anyone who follows it. The residual risk is organizational rather than technical: the new subdomain must not be advertised or used in ad campaigns until Phase 3 swaps in the real form ID. Recorded as an explicit flagged assumption in this plan's Planning notes and carried into the phase VERIFICATION. |
| T-01-04 | Tampering | `scripts/check-no-direct-typeform.mjs` build guard | medium | mitigate | The guard is the only mechanism preventing direct Typeform links from leaking into client-rendered components and bypassing host-based routing. Weakening it to accommodate the 4th brand is prohibited; the new literal is placed inside the already-allow-listed file instead. Enforced by prohibition and by `npm run prebuild` passing unmodified. |
| T-01-SC | Tampering | npm / pip / cargo installs | high | accept | This phase performs zero package-manager installs; `package.json` and `package-lock.json` are unchanged, so the supply-chain surface is unmodified. No Package Legitimacy Audit is required (RESEARCH.md confirms the audit is not applicable) and no legitimacy checkpoint is needed. Enforced by the Task 1 acceptance criterion that `git status --porcelain` shows `app/apply/page.tsx` as the only modified source file. |
